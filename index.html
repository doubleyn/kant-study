AI 시대, 개발자의 역할과 채용 기준

AI 활용을 위해 모델 학습이나 파인튜닝이 반드시 필요한 것은 아니다. 이미 성능이 좋은 모델을 잘 서빙하고, 추론에 필요한 프롬프트·컨텍스트·데이터를 구성하는 역량이 중요해지고 있다. 데이터의 의미를 이해하는 도메인 지식도 함께 필요하다.

AI가 코드 작성을 대신하더라도 무엇을 만들고 어떤 문제를 해결할지 정의하는 역할은 여전히 중요하다. 개발자 대체에 대한 불안보다 문제 정의와 효율적인 해결에 집중하라는 조언이다.

코딩 테스트는 사라지기보다 AI 사용을 허용하면서 더 어려운 문제를 해결하게 하는 방식으로 변할 수 있다고 전망한다. 여러 AI 도구를 사용해 봤다는 사실보다 실제로 무엇을 해낼 수 있는지가 평가 대상이다.

오픈소스 기여는 문서·테스트·PR 규칙을 따르고 검토와 병합을 경험한다는 점에서 실무 개발 흐름을 보여준다. 단순 구현을 넘어 유지보수, 사용자 피드백, 운영 비용까지 고려하는 역량이 요구된다.

빠른 지원과 실제 문제 중심의 프로젝트

오랫동안 준비한 뒤 한 번 지원하기보다 현재 역량으로 빠르게 도전하고, 서류와 면접의 반응을 통해 부족한 부분을 보완하는 방식을 권한다.

평가 기준은 무엇을 공부했는가에서 공부한 것으로 어떤 문제를 해결할 수 있는가로 이동하고 있다. 취업용 프로젝트라면 목표 기업이 해결하려는 문제를 추정하고 해결책을 만드는 것이 좋다.

강연자는 특정 직무의 키워드를 맞추기보다 하나의 서비스를 만들기 위해 클라이언트·앱·서버·웹 등 필요한 기술을 익혔다고 설명한다. 결과물을 만들고 사용자와 상호작용하며 네트워킹하는 경험을 강조한다.

AX 엔지니어의 다섯 가지 업무

① 문제 정의: AI로 해결할 가치가 있는 업무를 선택한다. ② 에이전트·워크플로 설계: 처리 흐름과 도구를 연결한다. ③ 데이터·컨텍스트 구성: DB, 데이터 파이프라인, RAG, 지식 베이스를 연결한다.

④ 평가와 품질 관리: 평가 데이터와 지표로 기대한 품질을 검증한다. ⑤ 배포·운영·개선: 실제 환경에서 비용, 지연 시간, 실패율을 관찰하고 개선한다.

특히 평가와 운영이 중요하다. API나 MCP를 연결해 답변이 나오게 하는 것으로 끝내지 말고, 프롬프트 변경이나 새 배포가 실제 품질 개선으로 이어졌는지 확인해야 한다. Langfuse·LangSmith 같은 LLMOps 도구를 경험해 보라고 권한다.

사내 규정 문의 에이전트의 전체 사이클

인사팀의 반복 문의를 자동화하는 예시다. 규정 문서를 모으고 청킹·메타데이터 정리를 거쳐 검색 기반을 만든 뒤 검색 → 근거 확인 → 답변 생성 흐름을 연결한다.

기업에서는 구현에 앞서 무엇이 필요한지 현업과 합의하고 도입 필요성을 설득하는 데 시간이 많이 든다. 이런 역할은 FDE와 맞닿아 있으며, 신입이라면 사수나 멘토의 지원 여부를 살펴보라는 조언이다.

구현 후 정답률과 정확도를 평가하고 실제 메신저 등에 배포해 문제를 관찰한다. 문제 선택부터 데이터 준비, 평가, 운영까지의 흐름은 포트폴리오 구성으로도 활용할 수 있다.

17:01–25:32AX 업무와 개발 기초

기초 질문 ① 프로그램은 어떻게 실행되는가

핵심 질문은 프로그램이 무엇인지, 아이콘을 더블클릭한 뒤 화면에 프로그램이 나타날 때까지 어떤 일이 일어나는지다.

강연에서는 프로그램을 코드와 데이터로 설명한다. 디스크의 코드와 데이터가 메모리에 올라가고 CPU가 명령어를 가져와 실행하며 결과를 반영한다. 운영체제는 여러 프로그램 사이에서 하드웨어 자원을 관리하고 실행을 조정한다.

이 구조를 알아야 문제가 생겼을 때 CPU·메모리·디스크 등 어떤 자원과 지표를 살필지 판단할 수 있다. CS 공부는 예상 답안을 암기하는 것이 아니라 동작을 이해하고 원인을 추론하는 기반을 만드는 과정이다.

모의 면접에서는 프로그램 실행에서 메모리, 프로세스, 스케줄링으로 꼬리 질문을 이어가며 이해의 빈틈을 확인한다.

25:32–32:54AX 업무와 개발 기초

기초 질문 ② 웹페이지는 어떻게 표시되는가

브라우저에 주소를 입력하고 엔터를 누른 뒤 페이지가 나타날 때까지의 과정을 설명할 수 있어야 한다. 외부 LLM API를 사용하는 AX 엔지니어도 서버와 클라이언트의 통신 기반을 알아야 한다.

DNS를 통한 도메인 이름과 IP 주소의 연결, 목적지까지의 라우팅, 스위치와 라우터, TCP 3-way handshake 등을 하나의 흐름으로 이해한다.

OSI 7계층은 이름을 암기하기보다 데이터가 계층을 거쳐 어떻게 전달되는지 설명하는 것이 중요하다. IP와 포트, 연결에 필요한 자원도 이 흐름 안에서 이해해야 장애 대응과 협업이 가능하다.

32:54–38:46AX 업무와 개발 기초

기초 질문 ③ LLM 응답은 어떻게 생성되는가

ChatGPT나 Claude에 프롬프트를 입력한 뒤 응답이 화면에 나타날 때까지의 과정을 설명하는 질문이다. 프로그램 실행과 네트워크 지식을 바탕으로 외부 모델의 추론과 결과 전달을 이해해야 한다.

추론 파라미터, temperature, Transformer, 어텐션, KV 캐시 등으로 이해를 확장한다. 용어 나열보다 시스템 구성 요소와 데이터 흐름을 자기 언어로 설명하는 것이 목표다.

프로그램 실행·웹 통신·LLM 응답이라는 세 질문을 중심으로 전체 그림을 만들면 다양한 기술 면접 질문에 대응할 기반이 된다. 도구 설치와 예제 실행을 넘어 효율적인 활용과 개선을 제안할 수 있어야 한다.

38:46–41:12평가와 실무 역량

RAG 평가: 검색과 답변을 분리해 검증하기

자연어 답변의 품질에도 평가 기준과 비교 가능한 측정 방식이 필요하다. LLM-as-a-Judge, precision, recall 등을 언급한다.

검색 품질은 질문에 적절한 근거를 가져왔는지, 생성 품질은 그 근거를 바탕으로 정확히 답했는지를 본다. 좋은 근거를 가져와도 답변 생성에 실패할 수 있으므로 단계를 분리해 원인을 찾아야 한다.

준비한 입력과 기대 출력으로 수행하는 오프라인 평가와 배포 후 실제 사용자의 예상 밖 입력을 관찰하는 온라인 평가를 함께 돌린다. 질문 몇 개에 그럴듯한 답이 나온다는 이유로 끝내면 충분하지 않다.

41:12–47:34평가와 실무 역량

AI 코드의 이해와 통제, 협업 태도

신입에게도 문제 정의부터 배포·평가·개선까지 한 사이클을 마친 경험이 중요하다. AI 사용 자체보다 작성된 코드의 동작과 구현 이유를 이해하는지를 본다.

강연자는 과제와 GitHub 코드의 특정 로직을 질문해 이해도를 확인한다고 설명한다. 장애 발생 시 AI가 그렇게 만들었다는 답 대신 원인과 해결 방향을 설명할 수 있어야 한다. 이해하지 못한 코드를 포트폴리오에 그대로 포함하는 것은 피한다.

기술을 쉽게 설명하고 관계를 원만하게 유지하며 팀으로 문제를 해결하는 태도도 중요하다. 새로운 기술을 보기만 하는 데서 끝내지 않고 직접 기능과 한계를 확인하는 실행력을 강조한다.

취업이 쉽거나 고소득이라는 기대만으로 진입하기보다 실제 업무와 지속적인 학습 방식이 자신에게 맞는지 점검하라는 조언이다.

47:34–54:02직무와 기업 선택

기업 유형별 요구 역량과 진로 선택

대기업은 특정 영역의 깊이, 장기 프로젝트, 여러 동료·이해관계자와 협업한 경험을 중요하게 볼 수 있다. 스타트업은 빠른 실행과 기술 도입, 여러 역할을 수행하는 능력을 요구할 수 있다.

기업 유형과 연차에 따라 기대하는 경험이 다르므로 향후 경력 이동 방향을 고려해야 한다. 스타트업 안에서 계속 경력을 발전시키는 길도 있다.

금융·제조 등에서는 특히 경력 채용 시 도메인 경험이 영향을 줄 수 있다. AI 전문 서비스 기업은 대형 모델 제공사가 유사 기능을 출시할 때 받을 사업 영향을 살펴야 한다는 견해를 제시한다.

컨설팅·에이전시는 기업 상황을 진단하고 AI 도입 로드맵, 필요 인력, 실행 방향을 제안하며 문서와 산출물 정리의 비중이 높을 수 있다. 원하는 업무 방식부터 정리하고 지원처를 선택한다.

54:02–57:22직무와 기업 선택

데이터 사이언티스트와 대학원 선택

데이터 사이언티스트는 데이터를 통해 의사결정을 돕는다. 모호한 현업 질문을 지표와 가설로 바꾸고 SQL 등으로 로그와 DB 데이터를 수집·정리한다.

실험 설계와 통계 검증, 필요시 모델 학습과 비교를 수행하고 대시보드·리포트로 전달한다. 확률·통계·선형대수 기반이 필요하므로 대학원을 고려할 수 있다.

장기 연구 주제는 현재 유행뿐 아니라 학위 이후의 가치도 고려해야 한다는 조언이다. 강연의 채용 공고 분석은 강연자가 약 3개월 전에 조사한 자료에 기반한다.

57:22–01:02:33직무와 기업 선택

AI 에이전트 엔지니어의 차별화 지점

개발 관점에서 에이전트를 단순화하면 LLM API에 컨텍스트·메모리·도구 실행 흐름을 결합한 프로그램이다. 모델에 도구 정보를 전달하고 사용 요청에 따라 도구를 실행한 뒤 결과를 돌려주는 과정이 포함된다.

직무 명칭과 정의가 아직 모호하므로 공고 검색 시 이름 하나에만 의존하지 않는다. 노코드 플랫폼에서도 에이전트를 만들 수 있어 단순 제작 경험만으로는 차별화하기 어렵다는 견해다.

평가 세트, 성능 검증, 배포 후 비용·오답 모니터링과 개선이 차별화 지점이다. LangChain·LangGraph·CrewAI 사용 자체보다 원리를 이해해야 한다.

FastAPI 서버 구성, Docker·Kubernetes 환경의 서비스 운영, Langfuse·LangSmith를 활용한 LLMOps 경험도 언급한다.

01:02:33–01:07:02직무와 기업 선택

LLM·온디바이스·피지컬 AI의 차이

LLM 엔지니어는 모델 서빙과 추론 최적화에 가깝다. GPU 동작, vLLM·Triton, 모델별 품질·성능 비교, 프롬프트·컨텍스트 최적화를 다루며 파인튜닝은 선택적으로 포함될 수 있다.

온디바이스 AI는 하드웨어 환경의 효율적 실행에 초점을 둔다. 양자화, 지식 증류, 런타임 최적화와 함께 메모리·발열 등 하드웨어 특성을 고려한다.

피지컬 AI·로봇은 코드뿐 아니라 하드웨어, 연결, 부품과 공급사 문제까지 원인을 구분해야 한다. 장비와 실험 환경의 접근성이 중요하므로 대학·연구기관과 연결된 환경이 도움이 될 수 있다.

이들 분야는 장비 사용과 연구 경험이 중요해 대학원이 유리할 수 있다. 실제 업무 범위와 부담, 본인의 흥미를 함께 고려한다.

01:07:02–01:12:46포트폴리오와 면접

포트폴리오: 문제 해결을 증명하는 기록

문제가 생기는 과정은 해결 역량을 보여줄 기회다. 무엇이 실패했고, 어떤 대안을 시도했으며, 왜 최종 방식을 선택했는지 기록한다.

문제와 목표, 시스템 구성도, 본인 담당 영역, 원인 분석, 해결 대안과 트레이드오프, 선택 근거, 결과와 수치를 담는다. 비용·성능·구현 난도 등의 기준으로 대안을 표로 비교하면 판단 과정이 잘 드러난다.

정답률, 근거 정확도, 평균 응답 시간, 질문당 비용 등의 변화를 제시한다. 강연의 정답률 62% → 84%는 수치 표현의 예시다.

README는 다른 사람이 이해·실행·인수인계하는 데 필요한 내용을 제공한다. 기술을 쓰려고 문제를 억지로 만들기보다 문제 해결에 맞춰 기술을 선택하고, 프로젝트 수보다 깊이를 보여준다.

01:12:46–01:19:48포트폴리오와 면접

기술 면접: 선택의 이유와 운영 관점

구현 가능 여부뿐 아니라 평가·운영·설계 선택을 질문한다. 성능 측정, 토큰 비용과 지연 시간, 환각 대응과 가드레일, 청킹 전략과 임베딩 모델의 선택 이유를 설명할 수 있어야 한다.

역질문으로 함께 일할 때 중요한 역량과 실제 업무 진행 방식을 물으면 조직의 기대를 이해하는 데 도움이 된다.

전공 여부보다 원리 이해와 근거 있는 설명이 중요하지만 특정 학위·연구 경험이 요구되는 직무는 다르다. 수학과 파인튜닝의 필요 수준도 직무에 따라 달라진다.

이력서의 메시지는 이것을 배웠다가 아니라 이것을 할 수 있고 이런 결과를 만들었다가 되어야 한다.

AI 활용 전 공식 문서와 예제를 참고해 API 하나 정도를 직접 만들 수 있는 기반을 권한다. 모든 문법을 암기하라는 뜻이 아니라 AI 코드의 필요성과 적절성을 판단할 기준을 갖추라는 의미다.
